# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 예외를 만들고 싶은 순간이 바로 이 규칙이 필요한 순간이다. 아래 절차를 글자 그대로 따른다.

## 0. 프로젝트별 규칙 우선 (Fallback 조항)

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 있으면 **그것을 우선**한다.
- **이 파일은 프로젝트 규칙이 없을 때의 기본값(fallback)이다.**
- 충돌 시: 프로젝트 규칙 > 이 파일.

## 1. 적용 기준

### TDD를 반드시 적용 (테스트 먼저)

- **비즈니스 로직** — 도메인 규칙, 계산, 상태 전이, 검증
- **API / 핸들러** — 요청/응답, 에러 매핑, 입력 검증
- **유틸 / 순수 함수** — 파싱, 변환, 포매팅
- **버그 수정** — 먼저 버그를 **재현하는 실패 테스트**를 쓰고, 그 테스트를 통과시켜 고친다

### TDD 불필요

- **타입 정의** — interface, type, 스키마 선언
- **설정 파일** — config, env, 빌드/린트 설정
- **순수 UI / 스타일** — 로직 없는 마크업, CSS
- **SQL / 마이그레이션** — 선언적 스키마·쿼리 (단, 쿼리를 감싸는 로직은 적용)

경계가 모호하면 **적용 쪽으로 판단**한다.

## 2. RED - GREEN - REFACTOR 사이클

### RED (실패하는 테스트)

- **하나의 동작 = 하나의 테스트.** 한 번에 여러 동작을 담지 마라.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다.
- 실패 이유가 **"기능이 아직 구현되지 않음"**이어야 한다.
  - 오타, import 오류, 컴파일 에러로 인한 실패는 **RED가 아니다.** 고치고 다시 확인한다.

### GREEN (통과시키는 최소 코드)

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI** — 지금 테스트가 요구하지 않는 기능·분기·추상화를 미리 만들지 마라.
- **신규 테스트 + 기존 테스트 전체**가 모두 통과하는지 확인한다.

### REFACTOR (구조 개선)

- 중복 제거, 이름 개선, 헬퍼 추출로 **구조만** 다듬는다.
- 리팩터 내내 **green을 유지**한다 (수시로 테스트 재실행).
- **새로운 동작을 추가하지 마라.** 새 동작이 필요하면 REFACTOR를 끝내고 RED로 돌아간다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 사이클을 작게, 여러 번 돈다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면**, 그 코드를 **삭제하고 RED부터 다시 시작**한다.
- **"참고용"으로 주석 처리하거나 남겨두는 것도 금지.** 눈에 보이면 최소 구현을 오염시킨다.
- 이미 작성한 코드가 아깝다는 감정은 규칙 위반의 근거가 되지 않는다. **지운다.**

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 30초면 쓴다. 단순하다는 판단 자체가 틀리는 곳에서 버그가 난다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 통과하는 코드에는 테스트를 쓸 동기가 사라진다. 지금 쓴다. |
| "시간이 없다" | 테스트 없이 디버깅하는 시간이 더 길다. TDD는 시간을 쓰는 게 아니라 아끼는 것이다. |
| "삭제하면 낭비다" | 검증되지 않은 코드는 자산이 아니라 부채다. 삭제 비용보다 잘못된 코드를 남기는 비용이 크다. |
| "프로토타입이다" | 프로토타입은 배포된다. "임시"가 영구가 되는 순간 테스트 없는 코드가 유산으로 남는다. |

## 5. 요약

**RED(실패 확인) → GREEN(최소 통과) → REFACTOR(green 유지) → 반복.**
테스트 없이 쓴 프로덕션 코드는 삭제한다. 변명하지 않는다. 프로젝트 규칙이 있으면 그것을 따른다.
