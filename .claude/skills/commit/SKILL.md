# commit

변경사항을 읽고 이해한 뒤, 관련된 것끼리 묶어 컨벤션에 맞는 한국어 메시지로 커밋한다.

핵심 목표는 **나중에 히스토리를 보는 사람이 "이 커밋이 무엇을, 왜 바꿨는지" 한 줄로 알 수 있게** 만드는 것이다. 그래서 변경을 뭉뚱그리지 않고 의미 단위로 나누는 것을 중요하게 다룬다.

## 절차

### 1. 변경사항 분석

무엇이 바뀌었는지 먼저 정확히 파악한다. 파일 목록만 보고 추측하지 말고 실제 diff 내용을 읽는다.

```bash
git status
git diff            # 아직 stage 안 된 변경
git diff --staged   # 이미 stage 된 변경
git log --oneline -10   # 이 저장소가 쓰는 메시지 스타일 참고
```

`git log`를 보는 이유는, 저장소마다 커밋 컨벤션(언어, prefix 사용 여부, scope 표기 등)이 다르기 때문이다. 기존 스타일이 이 스킬의 기본형과 다르면 **저장소의 관행을 우선**한다. 여기서 제시하는 형식은 관행이 없을 때의 기본값이다.

### 2. 논리적 단위로 분류

변경을 성격별로 묶는다. 판단 기준은 "이 변경들을 되돌린다면 함께 되돌려야 하는가?"이다.

- 서로 맞물린 변경(같은 기능을 위한 여러 파일 수정)은 한 커밋으로 묶는다.
- 성격이 다른 변경(새 기능 + 무관한 버그 수정 + 오타 교정)은 나눈다.
- 나눈 결과를 커밋과 함께 보고한다. "이렇게 N개 커밋으로 나눴습니다"라고 각 단위에 어떤 파일·변경이 들어갔는지 제시한다. (승인을 기다리지 않고 바로 진행한다.)

변경이 이미 하나의 일관된 작업이라면 굳이 쪼개지 않는다. 분할 자체가 목적이 아니라 "히스토리 가독성"이 목적이다.

### 3. 한국어 커밋 메시지 작성

형식: `<type>: <요약>`

| type | 쓰는 경우 |
|------|-----------|
| `feat` | 새 기능·동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정·빌드·의존성·잡무 |
| `docs` | 문서 변경 |
| `style` | 포맷·세미콜론 등 비기능 변경 |
| `test` | 테스트 추가·수정 |

요약은 한국어로, "무엇을 했는지"가 드러나게 간결히 쓴다. 왜 바꿨는지가 제목만으로 부족하면 본문에 개조식으로 덧붙인다.

**Example 1**
Input: JWT 기반 인증 미들웨어와 로그인 폼을 추가함
Output: `feat: JWT 인증 및 로그인 폼 추가`

**Example 2**
Input: 코드 생성 시 props 타입이 누락되던 문제를 고침
Output: `fix: 컴포넌트 생성 시 props 타입 누락 수정`

**Example 3**
Input: 템플릿 렌더링 로직을 별도 모듈로 분리(동작 동일)
Output: `refactor: 템플릿 렌더링 로직 분리`

### 4. 커밋 실행

승인을 기다리지 않고 바로 커밋한다. 단위별로 해당 파일만 stage 해서 커밋하고, 무엇을 어떤 메시지로 커밋했는지는 실행 후 사용자에게 보고한다.

커밋은 `git reset --soft HEAD~`로 쉽게 되돌릴 수 있으므로, 잘못됐을 때는 되돌리는 방법을 함께 안내한다.

```bash
git add <이 단위에 해당하는 파일들>
git commit -m "feat: 요약"
```

여러 단위면 stage → commit을 순서대로 반복한다.

## 주의사항

- **push는 하지 않는다.** 사용자가 명시적으로 요청할 때만 push한다. 커밋과 push는 별개의 결정이다.
- stage 전에 `.env`, 키·토큰 등 커밋되면 안 되는 민감 파일이 섞이지 않았는지 확인한다.
- 현재 브랜치가 `main`/`master`이면, 팀 관행상 직접 커밋이 맞는지 한 번 짚어주고 필요하면 브랜치 분기를 제안한다.
- attribution(예: `Co-Authored-By`) 규칙은 저장소·세션 지침을 따른다. 별도 지침이 없으면 넣지 않는다.
